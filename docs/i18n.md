# Internationalization

Termy's interface is available in English and Chinese. This page explains how
the translation layer works, how to write new UI text, and how to add strings or
another language.

## Choosing a language

```txt
language = auto   # auto | en | zh
```

The same option is under **Settings → Appearance → Language**. `auto` follows the
operating system's display language: Chinese systems get Chinese, everything
else gets English. Changing the value takes effect in every open window without
a restart.

System detection reads:

- Windows: `HKCU\Control Panel\Desktop\PreferredUILanguages`, then
  `HKCU\Control Panel\International\LocaleName`.
- Other platforms: the first non-empty of `LC_ALL`, `LC_MESSAGES`, `LANGUAGE`,
  and `LANG`.

## How it works

The English text is the key. Code writes `t!("New Tab")`; when the language is
Chinese the macro looks the text up in a table and returns the translation. A
missing entry falls back to the English text, so a forgotten translation shows
English and never breaks anything.

| Piece | Location |
| --- | --- |
| Language state, `t!` macro, lookup, system detection | `crates/desktop_app/src/i18n/mod.rs` |
| Setting type (`AppLanguage`), key `language`, choices | `crates/core/src/config_core/` |
| Translation tables | `crates/desktop_app/src/i18n/zh_*.rs` |

`i18n` lives in the library target (`termy`) so the library modules
(`auto_update`, `design_system`, `native_sdk`, `terminal_ui`) and the desktop
binary share one language state. Core stays free of UI text and of GPUI, and only
carries the `language` setting.

The language is applied when a window opens, when the config reloads, and when
the settings window changes the value.

### Translation tables

Each table is a list of `("English text", "中文译文")` pairs. They are split by
area only to keep files reviewable:

| File | Holds |
| --- | --- |
| `zh_core.rs` | Config schema titles, descriptions, groups, and enum labels |
| `zh_terminal.rs` | Command palette and menus |
| `zh_terminal2.rs` | Terminal view: runtime, tabs, interaction, persistence, overlays |
| `zh_terminal3.rs` | Terminal view: main render and mod, tab strip |
| `zh_settings.rs` | Settings window |
| `zh_app.rs` | Everything else: startup, updates, theme store, config errors, native dialogs |
| `zh_new.rs` | Later additions: shortcuts popup, tab menu, language setting |

The same English text may appear in several tables only with the same
translation.

## Writing UI text

Static text:

```rust
.child(t!("Rename Tab"))
```

`t!("…")` returns `&'static str`. Call `.to_string()` where a `String` is needed.

Text with values uses named placeholders and returns a `String`:

```rust
toast::error(t!("Failed to open {path}", path = path.display()))
```

- Use `{name}` only. Positional `{}` is not supported.
- For `{:?}`, widths, or precision, format the value first and pass the string.
- The translation must contain exactly the same placeholders as the English text.
- Write whole sentences. Do not build a sentence from translated fragments.
- Use separate keys for singular and plural (`"1 result"`, `"{count} results"`).

Text that cannot call a macro, such as a `const`, keeps its English value and is
translated where it is shown:

```rust
const UNAVAILABLE_HINT: &str = "unavailable";
// in the binary:   termy::i18n::tr(UNAVAILABLE_HINT)
// in library code: crate::i18n::tr(UNAVAILABLE_HINT)
```

`t!` itself needs no import in either target.

Settings rows, command titles, and enum choices come from core as English
`&'static str`. They are translated at the place they are drawn, and settings
search keeps matching the English keywords.

### What not to translate

- Log, panic, and assertion messages.
- Config keys, command ids, element ids, file paths, shell commands, environment
  variable names, and protocol fields.
- Strings that are stored or parsed back, for example a saved name that is later
  matched with `strip_prefix`.
- Product and technology names: Termy, tmux, SSH, Git, macOS, Windows, Linux,
  OSC, ANSI, PTY, GitHub, Bun.
- Text supplied by plugins or other programs, and raw error text passed through
  from them.

## Adding a translation

1. Wrap the string with `t!` (or `tr` for a `const`).
2. Add `("English text", "中文译文"),` to the table for that area. Search the other
   tables first (`grep -rn '"English text"' crates/desktop_app/src/i18n/`) and
   reuse an existing translation exactly.
3. Run `cargo test -p termy --lib i18n`.

Terms to keep consistent:

| English | 中文 | English | 中文 |
| --- | --- | --- | --- |
| Tab | 标签页 | Pane | 窗格 |
| Split | 分屏 | Workspace | 工作区 |
| Theme | 主题 | Settings | 设置 |
| Config | 配置 | Settings file | 设置文件 |
| Command palette | 命令面板 | Session | 会话 |
| Layout | 布局 | Plugin | 插件 |
| Task | 任务 | Shortcut / keybinding | 快捷键 |
| Scrollback | 回滚缓冲 | Working directory | 工作目录 |
| Tab bar | 标签栏 | Title bar | 标题栏 |

## Checks

The tests in `i18n/mod.rs` verify that:

- no English key has two different translations;
- no translation is empty;
- every translation keeps the same placeholders as its English text;
- a missing entry falls back to English;
- named values are substituted in both languages.

Nothing yet verifies that every `t!("…")` in the code has a table entry. After a
large change, compare the string literals passed to `t!` against the table keys
(a script that scans `crates/desktop_app/src` for `t!("…")` is enough); entries
that are missing only show up as English at runtime.

## Adding another language

1. Add a variant to `AppLanguage` in `crates/core/src/config_core/types.rs` and
   accept its names in `AppLanguage::from_str`.
2. Add a choice to `LANGUAGE_ENUM_CHOICES` and a case to the value mapping in
   `schema.rs`.
3. Add a variant to `Language` in `i18n/mod.rs`, a table set for it, and the
   system-language detection.
4. Regenerate the config docs: `just generate-config-doc`.

## Pitfalls

- **Never swap the global language temporarily.** Code that needs text in a
  language other than the current one (for example startup toasts built before
  `set_language` runs) must use `i18n::with_language`, which overrides the
  language for the current thread only. An earlier version swapped the global
  `CURRENT` value and restored it afterwards; with `language = auto` on a
  Chinese system, any parallel test that reached `load_runtime_config` made
  other threads read Chinese text for a moment, and dozens of English-asserting
  tests failed at random (they all passed when run alone). The same race would
  flicker the UI in the running app. If you add another "temporary language"
  helper, keep it thread-local and run the full `cargo test -p termy`, not just
  the tests you touched.
- **Do not parse translated text.** Return structured values (ids, enums) from
  functions and translate only at the display edge. Matching on a translated
  prefix breaks as soon as the UI language changes.

## Known gaps

- Plugin-supplied titles, options, and messages are shown as the plugin wrote them.
- Developer metric lines in the debug overlay stay in English.
- The translation work was built and tested on Windows. Code paths that only
  compile on macOS and Linux (native menus, system dialogs, the Linux clipboard
  prompt) were updated but not exercised.
- Outside Windows, system language detection reads locale environment variables,
  which may not match the display language for apps started from a launcher.
  Set `language` explicitly if `auto` picks the wrong one.
